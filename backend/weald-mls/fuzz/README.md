# Fuzzing the MLS binding

One target, `fuzz_targets/process.rs`. It drives `Session::process`, which is what
`weald_mls_process` marshals to and the one function in this crate that consumes
bytes from an untrusted network.

```sh
cargo install cargo-fuzz
cargo fuzz run process
```

The target asserts three properties rather than only the absence of a crash: it
never panics, it always answers with a typed `Status`, and the group survives, so
hostile input is dropped rather than absorbed. The header comment in the target
is the long form.

The corpus under `corpus/process/` is checked in rather than regenerated. It is
about 1,700 inputs and 7 MB, which is the bulk of a first clone, and it is here on
purpose: a corpus that lives only on a maintainer's laptop means every
contributor starts coverage from zero, and a regression the corpus already covers
gets rediscovered by nobody. Every input is machine-generated by libFuzzer from
previous runs. None of it is captured traffic and none of it carries a key: the
target builds its own device and group in memory on each process start.

`artifacts/` is gitignored and holds whatever a local run finds. A file appearing
there is a bug report with the reproduction already attached:

```sh
cargo fuzz run process artifacts/process/<file>
```

`slow-unit-*` files are timeouts rather than crashes. They are worth looking at
(a parser that takes a long time on a small input is a denial of service in
waiting) but they are not memory safety findings.

If you find a crash, `SECURITY.md` at the repository root rather than an issue.
Memory unsafety across this crate's C ABI is explicitly in scope.
