# RFC 9420 interop test vectors

The corpus `tests/vectors.rs` runs against. Vendored rather than fetched, because a
conformance gate that downloads its own evidence at test time is a gate that passes when
the network is down and changes what it proves without anyone approving a diff.

## Provenance

- **Upstream:** <https://github.com/mlswg/mls-implementations>, directory `test-vectors/`
- **Commit:** `89134d5de0222bd99598ba5849003d2e85e63116`
  (<https://github.com/mlswg/mls-implementations/commit/89134d5de0222bd99598ba5849003d2e85e63116>)
- **Raw URL pattern:**
  `https://raw.githubusercontent.com/mlswg/mls-implementations/89134d5de0222bd99598ba5849003d2e85e63116/test-vectors/<file>`

The vectors describe RFC 9420 and are generated by the MLS working group's interop
harness from several independent implementations, which is what makes them evidence about
our marshalling rather than evidence about OpenMLS.

## Files and digests

| File | SHA-256 |
| --- | --- |
| `crypto-basics.json` | `17cfcf89af9f51d0f2aa7af77f6f9ec99376a039214b6d42a6f11646b83e8c29` |
| `messages.json` | `b194abe1561995223482dbad51c180146920dc2f637e74d01e07a388308791fb` |
| `welcome.json` | `06be9d5c99817ef2545e4b15b8e73fd9b604685a8e55b59ca168eda98e236502` |

The same three digests are repeated in `tests/vectors.rs` (`CORPUS`) and re-derived on
every run by `the_vendored_corpus_is_the_one_this_suite_was_pinned_against`, using the
SHA-256 of the provider `src/store.rs` assembles. A file edited to make a failure go away
fails that test first.

To verify by hand:

```
shasum -a 256 backend/weald-mls/tests/vectors/*.json
```

To refresh (a deliberate act, not a maintenance chore): re-download at a new commit,
update the table above, update `UPSTREAM_COMMIT` and `CORPUS` in `tests/vectors.rs`, and
re-check the exact counts those tests assert, since a corpus of a different size changes
them.

## What is here and what is not

Only the files this suite actually drives are vendored. Everything else in upstream's
`test-vectors/` is named in `tests/vectors.rs` (`NOT_VENDORED`) with the reason it is out
of scope: either our one ciphersuite cannot express it, or it addresses OpenMLS internals
our twelve-function seam never sees, or it requires importing a joiner's private keys and
the seam has no import path by design.

Only the entries at
`MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519` (ciphersuite 1) are run, since that is the
one ciphersuite this build speaks (`session::CIPHERSUITE`, and `mls-binding.md`'s "no
custom ciphersuite"). The files are vendored whole anyway, so their digests match upstream
exactly and the filtering is visible in the test rather than baked into the data.
